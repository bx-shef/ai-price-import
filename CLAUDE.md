# AI-импорт прайсов (редизайн)

> Last reviewed: 2026-08-12

AI-импорт прайсов с табличной частью в Bitrix24. Облачное приложение Маркета
(мультитенант, OAuth), издатель ИП Шевчик И.С. Вход — любой документ с таблицей
(накладная/счёт/КП/прайс), суть — найти контрагента и внести товары в целевую CRM-сущность.

## Раскладка

`app/` — Nuxt (авто-импорт), `server/` — Nitro (api / routes / utils / queue / db / plugins /
agent), `prompts/` — промпт извлечения, `tests/` — автотесты, `scripts/` — живые проверки,
`telemetry-station/` — станция сбора телеметрии (вне сборки и CI), `legacy/` — старый проект
(не линтуется и не типизируется), `docs/` — документация.

⚠ **Инварианты подсистем живут в [`README.md`](README.md), раздел «Подсистемы» (в конце файла)**
(SEO лендинга, LLM-экстрактор, чат-бот, события установки, OAuth и SDK, пагинация, телеметрия,
тревоги очередей, форматы, пределы частоты, попап оценки, Вайбкод и защита без nginx). Они
переехали туда 11.08.2026 (#508) вместе с раскладкой: этот файл грузится в КАЖДУЮ сессию
целиком, а те правила нужны ровно тому, кто правит свою подсистему. **Правишь `server/` или
`app/` — открой README: правила оттуда обязательны так же, как здешние, они просто не грузятся
сами.** Два самых больших свода — в процессе: **запись в CRM** —
[`PROCESS.md`](docs/PROCESS.md) §15.1, **задание импорта и лента** — §15.2.

⚠ **Четыре правила из переехавших остаются ЗДЕСЬ**: их цена — чужие данные, а не кривой экран, и
знать о них надо до того, как откроешь README.

- **Своё дело, свой документ, свой портал — сужение по владельцу обязательно.** Журнал читает
  только дела сотрудника (`RESPONSIBLE_ID` из проверенного фрейм-токена), вложение к отзыву — тоже
  (`ownActivityFilter`). `jobId` присылает клиент: без сужения он вытащит чужой документ, и снаружи
  это неотличимо — отзыв уходит успешно в обоих случаях.
- **Портальные списки читаем токеном ПОРТАЛА, а сужаем СВОИМ фильтром.** Фрейм-токен сотрудника
  вернул бы разное разным людям, и дефект выглядел бы как «у одних работает».
- **`member_id` при установке сверяется с authoritative-значением** (#162): валидный токен своего
  портала с чужим `member_id` иначе отравляет привязку жертвы.
- **Адрес, по которому ходит НАШ процесс, проверяется на домен Битрикс24** (`isSafeB24Domain`), а
  не на схему, и переадресация не выполняется: подменённый адрес из ответа портала увёл бы
  серверный запрос на чужой хост.

## Команды

```bash
pnpm dev          # дев-сервер
pnpm lint         # ESLint
pnpm typecheck    # nuxt prepare + vue-tsc --build (Nuxt 4 split-tsconfig)
pnpm test         # Vitest (unit + nuxt)
pnpm test:unit    # только unit (чистое ядро)
pnpm generate     # SSG-сборка
pnpm check        # lint + typecheck + test
```

**Живые проверки** — нужен `.env.b24test`/`B24_HOOK` и ключ нейросети. Что именно каждая доказывает и
какие живые находки ими сняты — [`PROCESS.md`](docs/PROCESS.md) §14.13; там же читать ПЕРЕД правкой
скрипта, иначе легко «упростить» проверку до бутафории.

```bash
pnpm seed:b24       # посев тест-портала: компания с налоговым номером + товары с артикулами. ⚠ ТОЛЬКО тест-портал
pnpm sdk:smoke      # транспорт: profile + crm.item.list + burst 30 без QUERY_LIMIT_EXCEEDED
pnpm verify:chat    # экстрактор: --provider deepseek|bitrixgpt → ExtractedDocument (ru/be/kk)
pnpm live:crm --ai  # полный E2E: текст → нейросеть → runCrmSync → сделка+позиции+уведомление+очистка
pnpm live:crm --no-taxid  # запасная ветка заголовка (#440): у поставщика НЕТ налогового номера
pnpm verify:article # краевые случаи подбора по артикулу (#383)
pnpm verify:attach  # документ к отзыву читается из вложения дела (#461)
pnpm verify:idem    # два прогона одним jobId → created:false, дубля нет
pnpm verify:llm     # все классы отказа распознавания доезжают в чат целиком (#416)
pnpm verify:fail    # сообщения об отказе: доставка, обезвреживание, удаление
pnpm ab:prompt --runs 2   # A/B промпта извлечения против origin/main (#337/#342)
pnpm loadtest:123   # доказательство rate-limiter (RestrictionManager)
pnpm loadtest:queue # очередь под нагрузкой: backlog, дедуп, обрыв воркера, scale-out, ретраи
```

⚠ **Запреты и ловушки, которые нельзя узнать из имени команды:**

- **Параметр-свойства конструктора запрещены** в `server/`/`app/`/`prompts/`: живые скрипты гоняют
  продовый код через `node --experimental-strip-types`, а этот режим только СТИРАЕТ типы и кода не
  генерирует. Одно такое поле роняло `pnpm sdk:smoke` на разборе файла. Сборка через Vite синтаксис
  принимает, typecheck молчит, тесты зелены — ломается ТОЛЬКО живая проверка. Гард —
  `tests/stripTypesCompat.test.ts`.
- **Переменная окружения ВЫИГРЫВАЕТ у файла** (`scripts/lib/llmEnv.mjs`, `envFile.mjs`): на сервере,
  настроенном на bitrixgpt, файл с `deepseek` заставлял проверять НЕ ТОГО провайдера. Пустое значение
  считается «не задано» и уступает файлу. Гарды — `tests/llmEnv.test.ts`, `tests/envFile.test.ts`.
- **Ключи провайдера перечислены ПОИМЁННО**, а не «всё из .env»: рядом лежат вебхук портала, пароль
  оператора и ключ шифрования токенов, а процесс отправляет текст документа наружу.
- ⚠ **Мажоры зависимостей.** TypeScript 7 ВЗЯТЬ НЕЛЬЗЯ: нативный порт с другой раскладкой пакета (нет
  `typescript/lib/*` в exports) — vue-tsc падает `ERR_PACKAGE_PATH_NOT_EXPORTED`. `pnpm.overrides` на
  транзитивную зависимость пишем **со скоупом родителя** (`minimatch@3>brace-expansion`), не голым
  именем, и клампим сверху (`uuid: >=11.1.1 <12`). `@nuxt/test-utils` держим на 4.0.x: 4.1 тянет h3
  v2-rc, а Nuxt 4.5 живёт на h3 v1.

## Интерфейс — правила, обязательные к соблюдению

### Библиотека

Интерфейс собирается **только на компонентах Bitrix24 UI (`b24ui`)** — своих кнопок, полей и
карточек не рисуем. Это требование Маркета: приложение обязано выглядеть частью портала. Нужного
компонента в библиотеке нет ⇒ сперва обсуждаем, а не рисуем свой.

Первоисточник — [LLM-индекс библиотеки](https://bitrix24.github.io/b24ui/llms.txt); оттуда же
[компоненты](https://bitrix24.github.io/b24ui/raw/docs/components/),
[дизайн-система и цвета](https://bitrix24.github.io/b24ui/raw/docs/getting-started/theme/design-system.md),
[CSS-переменные](https://bitrix24.github.io/b24ui/raw/docs/getting-started/theme/css-variables.md),
[`useDevice`](https://bitrix24.github.io/b24ui/raw/docs/composables/use-device.md),
[`useToast`](https://bitrix24.github.io/b24ui/raw/docs/composables/use-toast.md),
[правила для ИИ-ассистентов](https://github.com/bitrix24/b24ui/blob/main/AGENTS.md) и
[рецепты](https://github.com/bitrix24/b24ui/tree/main/skills).

**Каркас всех in-portal экранов — официальный шаблон** (#259): `B24DashboardGroup` в layout,
`B24DashboardPanel` на странице, шапка — `B24DashboardNavbar`. Сайдбар и командную палитру шаблона
**не берём** (разделы открываются слайдером портала), а `fixed inset-0` базы шаблона переопределён:
высоту iframe портал подбирает по контенту, и фиксированная оболочка здесь неприменима.

### Цвет — только именем роли

Хардкод цвета (`#0d6efd`, `red`) запрещён: портал сам подставляет оттенок и сам переключает тему.
Роли `B24Button`: `air-primary` (главное действие, одно на экран) · `air-primary-success` ·
`air-primary-alert` (необратимое) · `air-primary-warning` · `air-primary-copilot` (ИИ-акцент) ·
`air-secondary`/`air-secondary-accent` · `air-tertiary-no-accent` (тихие: «Отмена», «Обновить») ·
`air-boost` (маркетинговый CTA). Текст и фон — `--ui-color-base-1…5` (от основного к тихому) и
`--ui-color-accent-main-primary|success|warning|alert`.

⚠ **Подложка страницы — `--air-theme-bg-color`, поверхность карточки — `--ui-color-bg-content-primary`**;
перепутать значит покрасить экран белым по белому. ⚠ **Что не влезает на экран — того нет**: журнал
единственный неограниченно длинный блок, поэтому метрики стоят **выше** него, а баннер издателя —
**врезкой ВНУТРИ ленты после третьей записи** (#507: сверху он занимал на телефоне целый экран
перед тем, ради чего приложение открывают; на портале с двумя записями его нет вовсе). ⚠ Строка
про баннер до 11.08.2026 утверждала обратное — «баннер выше журнала» — и ссылалась на
`tests/portalShellLayout.test.ts` как на своё доказательство, хотя тот с #507 требует
противоположного. Оба правила держит он же, разбор — [`PROCESS.md`](docs/PROCESS.md) §14.15.

⚠ **Обе темы обязательны**, и специально ничего не перекрашивают: на токенах тема переключается
сама. ⚠ Это правило действует **внутри портала**; публичные страницы (лендинг, юридические) живут
на обычном Tailwind с парой фон+текст из `app/config/landingShell.ts` — прочитанное буквально, оно
уже воспроизвело #368.

### Мобильное приложение Б24

Факт запуска в мобильном клиенте определяется **средствами b24ui** (`useDevice().isBitrixMobile`,
по User-Agent), а не JS SDK. Отдельного макета нет — тот же экран без своего заголовка (клиент
рисует свой), без шестерёнки настроек и без ссылки на подробные метрики: и то и другое правят с
компьютера, на узком экране форма и таблица не читаются.

⚠ **Скрывать условным рендером, а не `display:none` по ширине**: спрятанное CSS-ом остаётся в
дереве, читается скринридером и занимает место. ⚠ Область нажатия — минимум 44×44 px. ⚠ Никакой
горизонтальной прокрутки; длинные имена файлов переносятся, а не обрезаются в никуда.

### Слайдеры

Настройки и метрики открываются **слайдером поверх работы**, ширина **720** — и это следствие
вёрстки, а не круглое число: 720 − 48 горизонтальных отступов = 672 px полезной ширины, а снизу
граница жёсткая — 640 px это точка переключения на мобильную раскладку, и внутри слайдера она
считается от ширины самого слайдера. Уже 640 ⇒ десктопный слайдер молча получает телефонный вариант
экрана.

⚠ **Колонка контента ширину НЕ капает**: ширину задаёт слайдер, а наше дело — **один горизонтальный
отступ у шапки и у содержимого**, и он один на все экраны (`app/config/portalShell.ts`). Длинные
абзацы капаем точечно, карточки — нет. ⚠ **Перекрывая класс компонента b24ui, пиши утилиту ТОЙ ЖЕ
формы и покрывай ВСЕ его брейкпоинты**: `px-*` не вытесняет `ps-*`/`pe-*` — у `tailwind-merge` нет
такого правила конфликта, оба класса доезжают до браузера, и там побеждает не наш. Цена — правка,
которая выглядит сделанной и молчит.

⚠ **Раскладка `/app` — две ячейки, и только от `lg`**: справа липкая зона загрузки, слева стопкой
экономия, баннер, журнал. Порог не произвольный: слайдер 720 остаётся НИЖЕ него. ⚠ Ячейки именно
ДВЕ: блоки разной высоты в одном ряду сетки дают дыру под коротким, и растягивание её только
переносит внутрь карточки. ⚠ Порядок в разметке — загрузка первой (на телефоне он становится
порядком экрана); места в сетке задаются `lg:col-start-*`, а не порядком блоков. ⚠ **Липкость шапки
и загрузки НЕ проверена вживую**: `sticky` работает, только если прокручивается наш документ, а во
фрейме портала высоту подбирает Битрикс24 и прокручивает страницу сам. Всё это держит
`tests/portalShellLayout.test.ts`, разбор — [`PROCESS.md`](docs/PROCESS.md) §14.15. Ссылка на созданную запись тоже открывается слайдером, а **не новой вкладкой** — человек не
теряет контекст.

### Тексты

Приведены к этим правилам в коде; правка интерфейса обязана их сохранять.

1. **Простые слова.** Никаких «сущность», «идемпотентность», «маршрутизация», «валидация» — «запись»,
   «сделка», «правило», «проверка». В интерфейсе пишем «сделку», «счёт», «лид», а не «сущность».
2. **Ожидается нажатие — пишем про нажатие**: не «Выберите свойство каталога», а «Нажмите и
   выберите свойство каталога».
3. **Ошибка отвечает на три вопроса: где, что, что делать.** ❌ «Валюта USD отсутствует в портале»
   ⇒ ✅ «Импорт остановлен: валюты USD из документа нет в вашем Битрикс24. Добавьте её в CRM
   (Настройки → Валюты) и запустите импорт снова.»
4. **«Стоп» и «предупреждение» — разное.** Ошибка (красная) начинается со слов «Импорт остановлен:»
   и означает, что в CRM не записано ничего. Предупреждение (жёлтое) — записали, но есть нюанс.
5. **Кнопка подтверждения именует действие**, а не «Да»: «Да, очистить», «Да, обнулить».
6. **Подтверждение встроенное, не `window.confirm`**: внутри iframe системное окно выглядит чужим.
7. **Действие в процессе — глагол «мы»**: «Отправляем…», «Сохраняем…», «Обновляем…».

### Доступность

Контраст не ниже AA в обеих темах (обеспечивают токены `--ui-color-base-*`); у каждой иконочной
кнопки — `aria-label`; смена статуса объявляется голосом (`role="status"`); всё управляется с
клавиатуры, фокус видимый.

### UX-решения, которые НЕ переизобретать

Каждое куплено разбором или живым прогоном, поэтому живёт здесь, а не в описании экрана.

- **Не показывать действие, которое не сработает** (#411): не-админ видит не кнопку, а указание, к
  кому идти. Скрытая кнопка **не** заменяет серверный гейт — разрешает действие только сервер.
- **Блокируется действие, а не выход из него.** На время пачки гаснут разрушительные кнопки;
  «Отмена» подтверждения обязана остаться живой, иначе человек заперт в подтверждении до конца
  прогона (#475). ⚠ Замок — настоящий `:disabled` НА КАЖДОЙ кнопке: `pointer-events-none` держит
  только мышь, с клавиатуры такая кнопка нажимается. ⚠ Погасили — **скажите словами, почему**:
  выключенная кнопка без объяснения неотличима от сломанной. ⚠ Гард берёт РОВНО СВОЙ тег, а не окно
  вокруг подписи: окно находило `:disabled` у соседней кнопки и пропускало снятие защиты.
- **Импорт — только по нажатию**: человек должен успеть проверить список и выставить «Куда».
- **Цель — одна на пачку**, контрол под списком: грузящий два десятка накладных выставлял бы одно и
  то же двадцать раз. Нужно разделить — делает две пачки.
- **Строка уходит из списка отобранных в момент ПЕРЕДАЧИ**: иначе документ висит в двух списках в
  двух состояниях; карточка и «Отменить» остаются смонтированными на весь прогон.
- **Упавший файл не останавливает пачку.** Единственное исключение — отказ по частоте загрузок: он
  про человека, а не про файл.
- **Список результатов живым остаётся всегда** — ради него страница и ждёт под баннером «не
  закрывайте страницу».
- **Согласие на передачу документа — отдельный шаг, а не галочка** рядом с комментарием: это самый
  юридически нагруженный элемент интерфейса, и он не должен читаться как оформление.
- **Наш отказ — к разработчику, отказ портала — к администратору** (#506, `pipelineFailure.ts`):
  сырой текст чужой ошибки наружу НЕ идёт, свои — по белому списку; ведём по шагам («откройте файл
  сами» → «пришлите разработчику»). ⚠ Извлечение чистит текст (`textSanitize.ts`): нулевой байт
  доезжал до записи в базу.
- **Мёртвая ссылка хуже отсутствия ссылки** — негодный адрес убирает блок целиком, а не ведёт в
  «примерно туда».
- **Пассивный индикатор ≠ визард.** Стадии задаёт сервер, поэтому стёпер не кликабелен и мелок
  (16 px против 28 у штатного `B24Stepper`, который обещает переключение руками). Процент ушёл вместе
  с полосой прогресса — вместо него `role="status"` с названием стадии.
- **Цвет итога читает ИСХОД, а не факт завершения** (#507): нет успехов — красный, часть — жёлтый,
  отмена — нейтральный; вид ставится вместе с текстом (`setNotice`). ⚠ Строки **переносятся, не
  `truncate`**. ⚠ Баннер издателя — врезка **внутри ленты** после третьей записи (значит на пустом
  портале его нет вовсе), карточка «Экономия» в мобильном приложении скрыта. Разбор — §14.15.
- **Не «коробка в коробке».** Проблемы и ошибка внутри карточки операции — цветная полоса слева, а
  не `B24Alert` со своей рамкой и иконкой. Вне карточки `B24Alert` остаётся штатным.
- **Операция — отдельная карточка с рамкой:** у неё несколько ярусов (файл, шаги, результат,
  проблемы, оценка), и без рамки соседние операции сливаются.
- **Окно оценки не перекрывает результат импорта**: он остаётся виден или становится первым, что
  человек увидит после закрытия. Просьба об оценке приходит после удачи — единственного момента,
  когда человек только что получил то, за чем пришёл.
- **Дизайн служебной зоны (`/login`, `/queues`) намеренно не прорабатывается** — это консоль
  владельца, а не продукт.
- **Смарт-процессы выбираются по названию**, а не «введите ID типа 1044». Один-единственный вариант
  уровня подставляется сам и не показывается. ⚠ Удалённая воронка на экране импорта **не дочищается
  молча** — весь маршрут уходит в «Авто» с сообщением (#488); прежняя формулировка «очищается, а не
  рисуется» описывала ровно то поведение, которое #488 объявил дефектом.
- **Экран не утверждает того, чего не знает** (#408) — до прихода данных заглушка, а не значения по
  умолчанию: на медленной сети подмена читается как сброс настроек.

- **Документация — три файла** (`docs/PROCESS.md` / `PROJECT_MAP.md` / `BACKLOG.md`) плюс материалы

  2026-07-29). Гвард — `tests/docsStructure.test.ts`. Исключение — материал **для внешнего

  список поимённо (так появились `PRICING.md` #301, `eula.md` #297, `market-graphics.md` #387,

  пятый источник обязательств, который никто не сверяет; `contracts.md` #419 — договор, счёт и акт:

- **Язык комментариев — по назначению, а не «всё на английском»** (правило приведено к фактической
  практике 08.08.2026; прежняя редакция требовала английский везде, и её нарушала бо́льшая часть

  - **короткий JSDoc «что это»** — английский. Он читается вместе с сигнатурой, а имена в коде

    Писать их на неродном языке значит платить точностью за единообразие — а точность здесь и есть
    весь смысл;
  - **пользовательский текст, документация, сообщения об ошибках** — русский, без исключений.

- **Факт настройки портала — флаг `configured`, а не сравнение с дефолтами** (#373): `writeMapping`

  появления флага; новые признаки настройки в них добавлять не нужно.
- **Ориентир ставки часа подставляется в поле при ЧЕТЫРЁХ условиях сразу** (#311, чистая
  `shouldPrefillRate`, данные — `app/config/hourlyRateHints.ts`): поле **пустое** (иначе затрём

  каждом открытии, и одно постороннее «Сохранить» записало бы цифру, которую админ не выбирал.

- **Объявление издателя — окно на компьютере, шторка на телефоне** (#469). Владелец пишет его в

  СЕРВЕР** той же функцией, что и публикацию; ⚠ **SVG запрещён** (документ со скриптами), только
  png/jpeg/webp/gif до 256 КБ; ⚠ ссылка разбирается `new URL`, а не префиксом; ⚠ идентификатор
  считается ОТ ВРЕМЕНИ публикации; ⚠ недоступное хранилище — «объявления нет», а не 502, но

## Workflow / Git

- **В `main` не пушим — только через PR.** Ветка сессии — из контекста. Мержит владелец
  (в этой сессии — по явному разрешению, если уверен, что не ломаешь).

## GitHub API Rate Limits

Квоты раздельные: REST-core (5000 запросов/час) и GraphQL (5000 очков/час). MCP-инструменты записи/
поиска/листинга идут через GraphQL — батчить записи, не молотить list/search в цикле. Читать прямым
REST где можно. Помнить про secondary limits (≈80/мин, 500/час на контент-операции) → backoff с jitter.
