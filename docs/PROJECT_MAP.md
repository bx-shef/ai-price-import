## 1. Общее состояние

Проект **переписан** со старой раскладки (4 отдельных сервиса: backend, MCP-сервер, UI,
PHP-модуль в коробке) на **единый процесс Nuxt 4 + Nitro**. Старый код лежит в `legacy/` — только
как источник для переноса удачных кусков, новыми проверками не покрывается.

Ядро работает и подтверждено вживую. До публикации в Маркете осталось закрыть гейты (§7).

**Автотесты:** 1402, зелёные в CI на каждый PR. Проверки: `pnpm check` (линт + типы + тесты).

| Страница управления токенами | ✅ проверено | Карточка на `/queues`: статус + «Переавторизовать» |
| Операторская консоль: список упавших задач | 🧪 сделано | Число «ошибки: N» раскрывается в список с причиной, временем и числом попыток; действия «Повторить» и «Отбросить». Раньше это был тупик — а ради него консоль и открывают. Механизм повторов проверен нагрузочным прогоном (#267). UX-замечание #271-B |
| Операторская консоль: живые данные и честные подписи | 🧪 сделано | Автообновление раз в 12 с с паузой и отметкой времени, признак «данные устарели»; у каждого блока своя ошибка и пустое состояние; сообщения гаснут сами; блокируется только своя строка; «Отзыв оставлен» — в два шага. Счётчики подписаны «в хранилище» (очередь считает сохранённые задачи, а не итог за всё время), выдуманная полоса прогресса заменена оценкой времени разбора. UX-замечание #271, независимая часть |
| Операторская консоль: настоящий итог, поиск порталов, `member_id` | 🧪 сделано | Рядом со счётчиками очереди (они показывают лишь то, что ещё хранится) — строка «по всем установленным порталам» из собственных счётчиков: это и есть настоящий объём. Не «за всё время» — при удалении приложения счётчики портала стираются, и об этом сказано прямо на экране; отказ базы не притворяется пустотой. Список порталов получил поиск по домену и `member_id`, отбор «только с проблемой» и порядок «сломанные наверх» — иначе портал с умершим токеном тонет среди здоровых. `member_id` виден в строке и копируется по клику: все действия идут по нему, а на экране был только домен. UX-замечание #271-C/J/K |
| Сообщение сотруднику и в чат ошибок при отказе | 🧪 сделано | Раньше об отказе знал только тот, кто сам заглянет в свой список операций. Теперь приложение пишет **загрузившему** в личный чат (кто это — из `profile` проверенного фрейм-токена; хранится только как адрес чата, в браузер и в консоль не отдаётся) и **в чат ошибок** админа (с номером задания — иначе отказ не найти, серверного списка нет). Покрыты **все четыре** способа закончиться неудачей. Отказы приходят пачкой, и приглушать её мы намеренно не стали (решение владельца): админ получает сообщение **на каждый** неудавшийся документ — десять одинаковых подряд и есть диагноз «сломалось системно». Повтор по одному заданию невозможен (право берётся один раз — и отдельно для сообщения, которое ветка записи в CRM шлёт сама; иначе переотправленное задание писало админу дважды). Частота загрузок ограничена на **входе** (40 на сотрудника за 10 минут, `outcome=rate_limited` в телеметрии): иначе пачка негодных файлов давала пачку сообщений в чужом чате. Считаем по сотруднику, а не по адресу — портал сидит за одним IP, и лимит по адресу душил бы коллег; портал без id сотрудника считается целиком (fail-closed). Упёршись в лимит, интерфейс **останавливает пачку** и показывает срок ожидания, а не перебирает оставшиеся строки с ложным «проверьте связь». ⚠ поток ограничивает, но не устраняет; счёт в памяти процесса — при размножении HTTP-роли переносить в Redis Внешний текст (имя файла, причина) обезврежен: разметка, **ссылки** (файл с именем «оплатите тут https://…» делал приложение отправителем фишинга), переводы строк, длина. Технический вывод `pdftotext`/`libreoffice` в чат не идёт — там внутренние пути. Решение «кому и что» — чистая функция с тестами. Описание — [`PROCESS.md`](PROCESS.md) §6.8; новая категория данных внесена в [`privacy-policy.md`](privacy-policy.md). ⚠ вживую сообщения ни разу не отправлялись |
| Архивация файла: закрыта гонка с записью дела | 🧪 сделано | Копия файла на Диск создавалась **после** постановки следующей стадии в очередь — на быстром документе дело успевало записаться раньше загрузки. Архивация перенесена ДО постановки (дубль при ретрае и так ловила идемпотентность загрузки; остаётся узкая щель на границе месяца — описана в коде). Плюс предупреждение в журнал, когда архивация включена, а ссылки нет: раньше пропажа была немой. ⚠ **Это упрочнение, а НЕ объяснение #263.** По датам git порядок не менялся с 16 июля, кнопка живёт с 19-го — тринадцать дней одного поведения не дают «раньше была, теперь нет» 28–29 июля. Под жалобу подходит #248 (28 июля): до него у сделки было **собственное** дело с кнопкой, после — одно дело на компании, а в сделке видно через привязку. Ведущая версия — что привязанное дело рисуется без кнопок; проверяется одним действием (открыть карточку компании), см. §12.1 |
| Вход оператора: понятный отказ, форма не обманывает | 🧪 сделано | Три причины отказа перестали выглядеть одинаково («Не удалось войти»): неверный пароль, вход выключен на сервере и сработавшая защита от перебора. При выключенном входе форма гаснет целиком (и гаснет, даже если пароль убрали уже при открытой странице); при переборе — **только кнопка**, с обратным отсчётом и авто-снятием: за nginx окно около шести секунд, и глушить форму до перезагрузки было бы хуже исходной беды. Заголовка `Retry-After` за nginx нет — подставляем короткий запасной срок. Вход считается включённым только при **обеих** переменных (пароль + секрет сессии): раньше при пустом секрете форма звала вводить пароль, а сервер гарантированно отказывал. Курсор сразу в поле. UX-замечание #271-M |
| Служебная консоль: заголовок и разбивка на разделы | 🧪 сделано | Заголовок переименован — на странице давно не только очереди. Полноэкранную оболочку `B24DashboardPanel`/`Toolbar` из замечания **осознанно не берём**: её база `fixed inset-0` убивает прокрутку на общих страницах и обнуляет высоту потока, по которой Битрикс24 подбирает высоту iframe (та же причина, что в §4). UX-замечание #271-L |
| Метрики: модель описана, валюта не выдумывается | 🧪 сделано | Таблица счётчиков и формулы — в [`PROCESS.md`](PROCESS.md) §7.1 (раньше модель жила только в коде). Захардкоженные «20 BYN/час» убраны: ставку задаёт администратор портала («Настройки» → «Экономия»), валюта — базовая валюта самого портала; ставки нет — денежной плитки нет, время остаётся. Изоляция счётчиков между порталами закрыта поведенческими тестами (запись/чтение/сброс на игрушечной таблице). UX-замечание #270; живая сверка на двух порталах — за владельцем |

### Попап оценки

После успешного импорта на главной всплывает предложение оценить приложение в Маркете — ✅
проверено. Решение о показе принимается **на сервере**: состояние хранится по порталу, повтор не
чаще раза в несколько дней, после перехода в Маркет попап замолкает до ручной проверки. Факт
оставленного отзыва Маркет по программному интерфейсу не отдаёт, поэтому владелец подтверждает его
сам из карточки «Оценки приложения» на `/queues`.

## 6. Инфраструктура

| Часть | Состояние | Комментарий |
|---|---|---|
| Очереди BullMQ + Redis | ✅ проверено | Четыре очереди: события, извлечение, распознавание, запись |
| Масштабирование воркеров | 🧪 сделано | Обработка — на N реплик; события и кроны — на одном |
| Единый транспорт к Битрикс24 | ✅ проверено | Официальный SDK со встроенным ограничителем |
| Ограничитель запросов к порталу | ✅ проверено | `pnpm loadtest:123`: 30 запросов подряд без отказа |
| Здоровье очередей: тревога вместо снимка | 🧪 сделано | `/queues` показывала **снимок**, а снимок не различает «навалило работы» и «всё встало» — 200 ждущих задач выглядят одинаково. Раз в 5 минут (крон-инстанс — один голос, а не по одному на реплику) проверяются три вещи: **«не разгребается»** — самая старая незакрытая задача висит дольше 20 минут; **«задачи падают»** — 10+ отказов за 15 минут; **«очередь не читается»** — отдельный вид тревоги, потому что при недоступном Redis счётчики отдают нули, и тотальная авария рисовалась бы пустой здоровой очередью. Тревоги в лог и на `/queues`; «ещё не проверяли» и «проверка отстала на полчаса» на экране отличаются от «всё хорошо». **Две неверные версии до этой** (обе описаны в коде, чтобы не повторить): дельта `completed`/`failed` между замерами — это размеры **урезанных** множеств (`removeOnComplete: 1000`), на нагруженной очереди дельта нулевая именно когда всё работает; и порог по **размеру** хвоста (50+) — привязывал тревогу к объёму, поэтому мёртвый воркер `b24-events` (единицы событий) не поймался бы никогда. ⚠ доставки наружу нет — тревогу надо увидеть; вживую не проверялось |
| Нагрузка на очередь | ✅ проверено | `pnpm loadtest:queue`: 2000 документов, ничего не потеряно |
| Повторы упавших задач | ✅ проверено | Седьмой сценарий нагрузочного прогона: ровно 3 попытки, пауза растёт кратно, неудачные лежат в своём списке с причиной, перемежающийся сбой доходит сам. Проверки подтверждены мутациями — при отключении повторов и при подмене паузы на фиксированную сценарий краснеет |
| Postgres: токены, счётчики | ✅ проверено | Миграции на старте |
| Статусы заданий в Redis с TTL | 🧪 сделано | 48 часов; серверного списка заданий нет |
| Телеметрия OpenTelemetry | 🧪 сделано | По умолчанию выключена; без адреса приёмника — пустышка |
| Docker-образы, выкладка | ✅ проверено | GHCR + Watchtower за общим nginx |
| Вариант «Вайбкод» (без nginx) | 🧪 сделано | Приложение само вешает защиту nginx |

**Реальная пропускная способность: ≈ 900 документов в час на портал.** Упирается в ограничитель
Битрикс24 (~2 запроса в секунду), а не в очередь. Очередь backlog держит и разгребает полностью.

## 9. Известные ограничения

Честный список того, что не покрыто:

- **Гонка при «зависшем» воркере.** Защита от дублей работает для последовательных повторов
  (воркер упал — задача вернулась). Случай «живой, но потерявший блокировку воркер параллельно со
  второй репликой» не воспроизводился и остаётся открытым.
- **Нагрузочный прогон — на модели.** Реальные вызовы к Битрикс24 в нём не участвуют; отдельно
  проверяется только ограничитель.
- **Не проверялось:** повторы упавших задач и поведение при ошибке обработчика, падение и возврат
  Redis/Postgres под нагрузкой, срок жизни статусов при очень длинной очереди, интерфейс под
  нагрузкой.
- **Стадия лида** подтверждена только на упрощённом портале.

## 10. Раскладка репозитория

```

```

**Соглашения:** комментарии в коде — по-английски, всё, что видит пользователь, и документация —
по-русски. Чистые функции отделены от ввода-вывода и покрыты тестами. Данные из портала выводятся
только через экранирование.

## 12. Чек-лист приёмки

То, что **нельзя** закрыть автотестами — прогоняется руками на тестовом портале перед выпуском.
Заменяет прежний развёрнутый чек-лист: там были те же сценарии, расписанные подробнее.

### 12.1. Короткий заход: восемь проверок, которые сейчас держат работу

Полный чек-лист ниже — для выпуска. Этот — **разблокировочный**: восемь пунктов, каждый снимает
конкретную задачу, которая иначе останется в состоянии «сделано, но вживую не проверено».
Порядок такой, чтобы не переоткрывать одно и то же место дважды.

| # | Что сделать | Что должно получиться | Кого разблокирует |
|---|---|---|---|
| 1 | Открыть адрес приложения **прямой ссылкой в браузере**, не из портала | Не пустой экран и не ошибка: страница объясняет, что приложение работает внутри Битрикс24, и ведёт в портал | #258 → за ним #262 |
| 2 | Открыть **карточку компании** по любому импорту, где дело записалось | Кнопка «Исходный файл» **есть на компании, но её нет в сделке** → привязанное дело не рисует кнопки, лечится сменой владельца дела на созданную сущность. Кнопки нет **нигде** → дело в архивации, смотреть журнал | #263, решающая проверка |
| 3 | Загрузить заведомо негодный файл (пустой PDF) и посмотреть в Битрикс24 личный чат | Пришло сообщение от приложения: имя файла, причина по-человечески, ссылка «открыть приложение». В чате ошибок — то же плюс номер задания, без имени сотрудника | Отправка сообщений, ни разу не проверена вживую |
| 4 | Настроить целью **«Смарт-счёт»** на портале, где смарт-счета выключены, и загрузить документ | В строке результата — «Не удалось внести документ в „Смарт-счёт“ — этот тип недоступен…», а не «Сущность CRM не поддерживается». Заодно: показывает ли `crm.item.fields` для типа 31 отказ или всё-таки поля | #263, #269 |
| 5 | На **свежем** портале (там всего ~5 единиц измерения) загрузить документ со «шт», «упак», «компл» | Единицы, которых в портале нет, не записываются молча: подставляется значение по умолчанию + предупреждение в списке проблем | #265 |
| 6 | Открыть «Настройки» → «Экономия», задать стоимость часа, вернуться на главную | Появилась плитка «Сэкономлено денег» **в валюте этого портала**. Стереть ставку — плитка исчезла, время осталось | #270, часть 1 |
| 7 | **Второй портал**: сделать импорт на A, открыть метрики на B | Счётчики B не изменились. Затем «Обнулить счётчики» на A — у B всё на месте | #270, часть 3 |
| 8 | Оттуда же: 👍 на строке результата портала A | В счётчиках B отзыв не появился | #270, часть 3 |

Пункты 1–6 делаются на одном портале и занимают минуты. Пункты 7–8 требуют **второго портала** —
без него изоляция метрик остаётся подтверждённой только тестами.

### 12.2. Полный чек-лист выпуска

**Установка и права**
- [ ] Установка на чистый портал: события привязались, токен сохранён, `/install` показал диагностику.
- [ ] Удаление приложения: данные портала стёрты, повторная установка проходит заново.
- [ ] Не-администратор не может сохранить настройки (проверять **ответ сервера**, а не только вид формы).
- [ ] На ненастроенном портале рабочая часть скрыта; администратор видит кнопку, сотрудник — текст.

**Разбор документа**
- [ ] PDF с текстовым слоем, PDF-скан, фото с телефона, Excel, Word — все доходят до CRM.
- [ ] Документ на белорусском и на казахском: метка налогового номера найдена.
- [ ] Файл не того формата, пустой, больше 20 МБ — понятный отказ, задание не создаётся.
- [ ] Съёмка камерой в мобильном приложении Битрикс24 открывает «Файлы / Фото / Камера».

**Деньги** (самое дорогое при ошибке)
- [ ] Цены с НДС и без НДС; разные ставки в строках; ставка 0 → «Без НДС».
- [ ] Печатный итог расходится с расчётом — предупреждение, сумма из сверенного расчёта.
- [ ] Строка со скидкой уменьшает сумму записи.
- [ ] Ставки НДС нет в портале / валюты нет в портале → импорт остановлен, сообщение в чат ошибок,
      в CRM **ничего не создано**.

**Подбор**
- [ ] Поставщик найден по налоговому номеру; не найден → запись без компании + предупреждение.
- [ ] Товар найден по торговому предложению, по свойству артикула, по внешнему коду, по имени.
- [ ] Товар не найден: обе настройки — пропуск строки и произвольная позиция.
- [ ] Незнакомая единица измерения → подстановка по умолчанию + предупреждение.

**Цели**
- [ ] Сделка, лид, смарт-счёт, смарт-процесс — каждая как цель.
- [ ] Правило по словам перебивает цель по умолчанию; ручной выбор для файла перебивает правило.
- [ ] Удалённое направление → запасная цель + предупреждение.
- [ ] Портал без лидов: вариант «Лид» скрыт, сохранённый лид уходит в сделку.

**Повторы и целостность**
- [ ] Повторная отправка того же файла не создаёт вторую запись (`pnpm verify:idem`).
- [ ] Пачка файлов: уходят по одному, статус по каждому виден.

**Результат в портале**
- [ ] Копия файла на Диске открывается по ссылке из списка операций.
- [ ] Запись в таймлайне видна **и** в компании, **и** в созданной сущности.
- [ ] Сообщения приходят в оба чата; разметка из документа обезврежена (`[url=...]` не сработал).

**Интерфейс**
- [ ] Светлая и тёмная тема на всех экранах.
- [ ] Мобильное приложение Битрикс24: нет дубля заголовка, скрыты шестерёнка и ссылка на метрики.
- [ ] Во время отправки списки заблокированы, дропзона объясняет почему.
