## 1. Общее состояние

Проект **переписан** со старой раскладки (4 отдельных сервиса: backend, MCP-сервер, UI,
PHP-модуль в коробке) на **единый процесс Nuxt 4 + Nitro**. Старый код лежит в `legacy/` — только
как источник для переноса удачных кусков, новыми проверками не покрывается.

Ядро работает и подтверждено вживую. До публикации в Маркете осталось закрыть гейты (§7).

**Как проект зарабатывает** ([`PRICING.md`](PRICING.md)): приложение **платное по подписке в
Маркете Битрикс24** (биллинг и лимиты — на стороне Битрикс24, поэтому счётчиков оплаты в коде нет и
не будет); отдельно оплачиваются доработка под процессы клиента, работа на его сервере (**по
запросу** — договорной формы и тарифа пока нет, #96) и
сопровождение. Конкретный тариф Маркета не выбран (§7).

**Автотесты:** около 1500, зелёные в CI на каждый PR. Проверки: `pnpm check` (линт + типы + тесты).

### Попап оценки

После успешного импорта на главной всплывает предложение оценить приложение в Маркете — ✅
проверено. Решение о показе принимает **сервер**; факт оставленного отзыва Маркет по программному
интерфейсу не отдаёт, поэтому владелец подтверждает его сам из карточки «Оценки приложения» на
`/queues`.

**Сроков два, и считаются они отдельно** (#380): не раньше четырёх суток от установки и не чаще
раза в четыре дня. Числа сегодня совпадают, смыслы разные. Почему именно так, откуда берётся дата
установки и почему неизвестный возраст означает «не показываем» — `CLAUDE.md`, блок про
`portal_app_rating`.

⚠ Подсказка-запись внутри окна — **синтетическая, из наших материалов** (решение владельца
2026-08-04): первая была снята с показа, потому что на ней стояла карточка ЧУЖОГО приложения.
Генерация — ручной `pnpm rating-demo`; правка логотипа или названия требует перегенерации.

## 11. Живые проверки

Требуют доступа к тестовому порталу и ключа нейросети (в репозиторий не коммитятся).

| Команда | Что проверяет |
|---|---|
| `pnpm check` | Линт + типы + все автотесты |
| `pnpm sdk:smoke` | Транспорт к порталу: 30 запросов подряд без отказа |
| `pnpm verify:chat` | Распознавание документа нейросетью |
| `pnpm live:crm --ai` | Полный проход: текст → нейросеть → сделка с позициями → уборка |
| `pnpm live:crm --no-taxid` | ЗАПАСНАЯ ветка заголовка записи (#440): у поставщика нет налогового номера ⇒ непроверенное название в заголовок не идёт, вместо него тип и сумма. Без флага у поставщика номер есть ВСЕГДА, то есть живьём наблюдалась ровно одна ветка из двух |
| `pnpm seed:b24` | **Не проверка, а подготовка портала**: компания с налоговым номером и товары с артикулами (+ само свойство «Артикул»). Идемпотентно, `--clean` убирает. Без него живой прогон уходит в ветки «контрагент не найден» и «товар не подобран», и обе выглядят штатно |
| `pnpm verify:article` | **Краевые случаи подбора по артикулу** (#383): неактивный товар, подстрочный ложняк (`ZQ-5` против `ZQ-50`), обе формы поля (запятая / строки с `\r\n`), внешний код без настроенного свойства и в другом регистре, несуществующее свойство. Зонды заводятся и убираются сами; гоняется НАСТОЯЩАЯ `findProduct`, а не переписанный запрос — иначе проверялась бы догадка сама на себе |
| `pnpm verify:idem` | Повтор одним идентификатором не создаёт дубль |
| `pnpm loadtest:123` | Ограничитель запросов к порталу (120 обращений, ни одного отказа) |
| `pnpm verify:llm` | Отказ распознавания доезжает в чат портала: у каждого класса своя формулировка, целиком, без строки провайдера, ключа и текста документа |
| `pnpm loadtest:queue` | Очередь под нагрузкой + реальный темп ограничителя |
| `pnpm ab:prompt` | A/B промпта извлечения против `origin/main`. Портал не нужен, нужен ключ нейросети. Без `--dir` берёт **обезличенный корпус в репозитории** (`corpus/prompt-ab`): его мало для значимости, но команда запускается в одну строку — иначе правило «перезамерь» обходят. Настоящий замер — `--dir <корпус>` с реальными документами **вне репозитория**. Обязателен перед правкой `prompts/extract.ts` — см. шапку файла |

То, что командой не проверить (глазами в портале), — в §12.1: заход по тому из помеченного 🧪, что
**даёт клиенту видимый эффект** — записи в CRM, сообщения, отказы, изоляция между порталами. Меток
🧪 в карте больше, чем пунктов в заходе: остальные (сверка `member_id`, надгробия, продление токенов,
масштабирование, телеметрия, вариант «Вайбкод») проверяются не глазами, а работой прода — их снимет
время, а не заход.
