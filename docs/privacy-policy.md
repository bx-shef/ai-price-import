Настоящая Политика описывает, какие данные обрабатывает приложение «procure-ai» (далее — «Приложение»)
при работе в облачном сервисе Bitrix24, с какой целью, куда они передаются, сколько хранятся и какие
права есть у пользователя. Устанавливая и используя Приложение, администратор портала Bitrix24
подтверждает, что ознакомлен с настоящей Политикой.

---

## 1. Какие данные обрабатываются

Приложение обрабатывает данные **только по инициативе пользователя** (загрузка документа) и служебные
данные, необходимые для интеграции с порталом Bitrix24:

| Категория | Что именно | Источник |
|---|---|---|
| **Документ с табличной частью** | Загруженный пользователем файл (накладная / счёт / КП / прайс): исходный бинарный файл и извлечённый из него текст/структура | Загрузка пользователем в интерфейсе Приложения |
| **Данные контрагентов из документа** | Наименования поставщиков, реквизиты (УНП/ИНН/БИН), номенклатура, цены, суммы, НДС — то, что содержится в документе | Содержимое загруженного документа |
| **Идентификатор портала** | `member_id` портала Bitrix24 и его домен | Событие установки / фрейм-токен Bitrix24 |
| **Идентификатор сотрудника портала** | `ID` пользователя Bitrix24, который загрузил документ — только как адрес личного чата, чтобы сообщить ему, если документ не удалось внести. Ни имя, ни почта, ни должность не запрашиваются | `profile` фрейм-токена Bitrix24 при загрузке |
| **OAuth-токены портала** | `access_token` / `refresh_token` / `application_token` для вызовов REST API портала | OAuth-авторизация Bitrix24 при установке |
| **Настройки Приложения** | Карта сопоставления (каталог, поле артикула, целевая сущность/направление, чаты уведомлений) | Ввод администратора портала |
| **Служебные счётчики** | Пожизненные агрегаты по порталу (сколько документов обработано/создано/не сопоставлено) — без содержимого документов | Формируются автоматически при обработке |

Приложение **не запрашивает** специальные категории персональных данных. Единственные данные,
которые Приложение собирает само, а не получает из документа или настроек, — идентификатор портала и
идентификатор загрузившего сотрудника (строки 3 и 4 таблицы); оба нужны для работы интеграции и
используются только как адреса — портала и личного чата.

## 2. Цели обработки

- Автоматическое распознавание табличной части документа и создание соответствующей сущности в CRM
  портала (сделка/лид/смарт-процесс с товарными позициями и НДС).
- Поиск контрагента в CRM портала по реквизитам из документа.
- Сохранение исходного файла на Диске портала и создание дела/уведомления в чат.
- Поддержание авторизации Приложения в портале (OAuth) и обеспечение работоспособности интеграции.
- Ведение обезличенных эксплуатационных счётчиков и (при явном включении администратором) технической
  телеметрии для диагностики и улучшения качества сервиса.

## 3. Куда передаются данные (важно)

### 3.1. Текст документа — на внешний LLM-провайдер

Для распознавания табличной части **извлечённый из документа текст** (включая наименования и реквизиты
контрагентов, номенклатуру и цены) передаётся на инференс **внешнему провайдеру больших языковых
моделей (LLM)**. Исходный бинарный файл на LLM **не передаётся** — только извлечённый текст.

> **Провайдер публичной версии — BitrixGPT** (AI Router сервиса Битрикс24 Вайбкод): извлечённый текст
> передаётся на инференс в инфраструктуру Битрикса, юрисдикцию данных на этом инференсе несёт Битрикс.
> Оператор Приложения (self-hosted) может выбрать иного провайдера настройкой окружения (напр. DeepSeek —
> юрисдикция КНР — только с информированным согласием клиента по 152-ФЗ/коммерческой тайне). Актуальный
> провайдер указывается в карточке Маркета.
>
> Сторонние модели (OpenAI, Anthropic и т.п.) AI Router использует **только** при подключении
> собственного ключа (BYOK). Публичная версия Приложения этого не делает.

### 3.2. Данные, остающиеся внутри периметра

| Данные | Куда | Примечание |
|---|---|---|
| Исходный файл документа | Кратковременно — диск сервера Оператора, затем (если включено в настройках) **Диск портала Bitrix24 клиента** | Копия на сервере Оператора удаляется **сразу после извлечения текста** — обычно в течение секунд. Дольше файл на стороне издателя не хранится. Если сотрудник прикладывает документ к отзыву, файл отправляет **сама страница** из памяти браузера, а не сервер. Наружу файл уходит только по явному ответу сотрудника, см. 3.3 |
| OAuth-токены портала | База данных backend издателя (Postgres) | `refresh_token` шифруется (AES-256-GCM); `application_token` — write-once |
| Служебные счётчики | База данных backend издателя | Скоуп per-portal; без содержимого документов |
| Настройки Приложения | `app.option` портала Bitrix24 | Хранятся средствами портала |

### 3.3. Отзывы сотрудников (по инициативе пользователя)

Если пользователь отправляет отзыв (👍/👎/💡) о результате обработки, текст отзыва и технический контекст
(что распозналось, какие возникли нестыковки) передаются в **закрытый (приватный) репозиторий издателя,
размещённый на GitHub** (GitHub, Inc., США).

**Вместе с отзывом может передаваться сам файл документа** (не ссылка на него) — **только если
отправитель явно ответил на вопрос «Приложить исходный файл?»**, который задаётся при нажатии
«Отправить». Вариант «Отправить без файла» предложен наравне с «Отправить с файлом»; ни один из них
не выбран заранее. Правило одно и то же для положительного и отрицательного отзыва: согласие на
передачу документа не зависит от того, понравился результат или нет (#299). При ответе «без файла»
уходит только текст отзыва и технический контекст.

Файл берётся **из памяти открытой страницы**: на сервере издателя копии уже нет (см. 4). Если
страницу перезагрузили или открыли в другой вкладке, приложение честно сообщает об этом и предлагает
выбрать файл вручную либо отправить отзыв без файла — молча отправить «пустой» отзыв оно не может.

Отзывы используются исключительно для устранения дефектов и улучшения качества сервиса.

### 3.4. Телеметрия (по умолчанию выключена)

Техническая телеметрия (OpenTelemetry) **по умолчанию отключена**. Включает её **Оператор Приложения**
настройкой своего окружения (администратор портала на это не влияет). При включении она
передаёт на коллектор издателя только «форму» операций (длительность, статус, обезличенные счётчики) и
**не содержит** коммерческих данных: идентификатор портала передаётся необратимым хешем, содержимое
документа/поставщик/артикул/цена в телеметрию не попадают (техническая защита на уровне кода).

### 3.5. Служебные оповещения о состоянии сервиса

Оператор может подключить канал оповещений (Telegram) для сообщений о неполадках собственной
инфраструктуры: какая очередь обработки встала, сколько задач не выполнилось. **Данные клиента туда не
передаются** — только имя внутренней очереди и числа. Ни документ, ни портал, ни сотрудник в этих
сообщениях не называются.

### 3.6. Публичное демо на сайте

На публичном сайте Приложения есть демонстрационный разбор: посетитель — **без установки Приложения и
без авторизации** — может загрузить свой документ и увидеть, что распозналось. В этом режиме
извлечённый текст передаётся тому же LLM-провайдеру (см. 3.1), результат показывается в браузере, файл
и текст **не сохраняются** и в CRM ничего не записывается. Для защиты от злоупотреблений фиксируется
IP-адрес обращения (счётчик частоты, во внешние системы не передаётся).

Демо адресовано посетителю сайта, а не порталу, поэтому раздел 5 «Права пользователя» применяется к
нему в части, не требующей идентификации: сохранённых данных, которые можно было бы выдать или
удалить, в этом режиме не образуется.

### 3.7. Сводка: кому и что уходит наружу

| Получатель | Что передаётся | Когда |
|---|---|---|
| LLM-провайдер (по умолчанию BitrixGPT / Битрикс24) | Извлечённый **текст** документа | При каждой обработке документа |
| GitHub, Inc. (США) — приватный репозиторий Оператора | Текст отзыва, технический контекст и **сам файл документа** | Только при отправке отзыва (см. 3.3) |
| Коллектор телеметрии Оператора | Длительности, статусы, хеш портала | Только если телеметрия включена Оператором |
| Telegram | Имена внутренних очередей и числа, **без данных клиента** | Только если Оператор подключил канал оповещений |

Больше наружу не уходит ничего: OAuth-токены, счётчики и настройки остаются в периметре (см. 3.2).

## 4. Сроки хранения и удаление

- **Статус задания импорта** — вместе с именем файла и идентификатором загрузившего сотрудника —
  хранится во временном хранилище (Redis) и удаляется автоматически по истечении срока жизни
  (по умолчанию — 48 часов). Идентификатор сотрудника нужен только чтобы сообщить ему о неудачном
  импорте; наружу, в интерфейс, он не отдаётся.
- **Извлечённый текст и структура документа** удаляются штатно в течение нескольких минут после обработки;
  дополнительно действует резервная очистка по расписанию (TTL-свип, по умолчанию — старше 24 часов).
- **Исходный файл** удаляется с сервера Оператора **сразу после извлечения текста** — обычно в
  течение секунд после загрузки. Резервная очистка по расписанию подметает только «осиротевшие»
  файлы заданий, не дошедших до обработки (сбой, перезапуск); её окно — часы, не сутки. Если в
  настройках портала включено сохранение файла, копия дополнительно кладётся на Диск портала клиента
  и управляется клиентом. Наружу издатель файл не выносит, за исключением п. 3.3 — по явному ответу
  сотрудника при отправке отзыва; в этом случае файл отправляет страница браузера, а не сервер.
- **OAuth-токены** хранятся в зашифрованном виде до удаления Приложения.
- **Удаление Приложения с портала** (`ONAPPUNINSTALL`) влечёт удаление данных этого портала на стороне
  издателя, хранящихся в базе данных: OAuth-токены, служебные счётчики, извлечённые текст/структура
  документов. Статусы заданий импорта хранятся во временном хранилище (Redis) и истекают автоматически
  по TTL (по умолчанию — в течение 48 часов).

Полный текст документов и секреты **не записываются** в общие журналы.

## 5. Права пользователя

- Получить сведения о том, какие данные обрабатываются, и цели обработки (по обращению к контакту выше).
- Прекратить обработку в любой момент — **удалив Приложение** с портала (влечёт удаление данных портала,
  п. 4).
- Запросить удаление конкретных данных или отзыва до истечения срока их хранения (по обращению).
- Отказаться от передачи текста на внешний LLM — не загружая документы (обработка инициируется только
  загрузкой).

## 6. Безопасность

- `refresh_token` портала шифруется в покое (AES-256-GCM); `application_token` пишется однократно.
- Все вызовы к порталу идут по защищённому транспорту с проверкой домена (защита от подмены).
- Доступ к настройкам и служебным операциям ограничен ролью администратора портала.
- Приложение минимизирует хранение: клиентские данные хранятся в минимальном объёме и удаляются на
  терминальных путях обработки и при удалении Приложения (передача текста на внешний LLM описана в п. 3.1).

## 7. Self-hosted (разворачивание на сервере клиента)

При установке Приложения на инфраструктуру клиента (self-hosted) приложение, база данных, очередь и
временные файлы остаются у клиента. Текст документа при этом всё равно уходит на внешний
LLM-инференс — self-hosted сам по себе не делает обработку полностью локальной.

**Существенное отличие от облачной версии: в self-hosted используется ключ провайдера, принадлежащий
клиенту.** Оператор своего ключа для таких установок не предоставляет. Это значит, что текст на
инференс отправляет клиент, по собственному договору с провайдером модели, и Оператор в этой передаче
не участвует и доступа к ней не имеет. Правовые основания и трансграничная передача при такой
отправке — на стороне клиента.

Полностью замкнутый контур (локальная модель на оборудовании клиента) — предмет отдельного соглашения. Ответственность за аптайм/бэкапы/патчи/защиту
ключей на инфраструктуре клиента определяется отдельным договором.
