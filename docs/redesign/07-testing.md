# План тестирования procure-ai

> Last reviewed: 2026-07-28

Трёхуровневый план проверки редизайна: от «вообще стартует» до «протестировано со всех сторон».
Уровни идут по возрастанию охвата и стоимости — проходим их по порядку, каждый следующий имеет
смысл только когда предыдущий зелёный.

> **Детальный чек-лист по подсистемам** (конкретные команды/ожидаемые результаты, метки
> [авто]/[вручную]/[нужен живой портал]/[нужен LLM-ключ]) — в
> [`10-qa-checklist.md`](10-qa-checklist.md). Этот документ — верхнеуровневая карта уровней;
> чек-лист — предметные строки для прогона.

- **Уровень 1 — «просто запустить»** (smoke): за пару минут убедиться, что ничего не падает на
  старте. Внешних сервисов (Redis/Postgres) не нужно.
- **Уровень 2 — «просто прогнать»** (happy-path): один раз пройти штатные сценарии. Часть требует
  `docker-compose` (Redis+Postgres) и/или живого тестового портала Б24.
- **Уровень 3 — «со всех сторон»** (полное покрытие): граничные случаи, безопасность,
  отказоустойчивость, регрессия.

Команды и роуты — из `package.json` и `server/api/*`; живой REST проверяем по вебхуку `B24_HOOK`
(скоупы `crm, catalog, disk, im`), а не по памяти.

## Уровень 1 — просто запустить (smoke)

Цель — стартует ли вообще. Критерий прохождения: всё поднялось, health отвечает, страницы не белые.

| Шаг | Команда / действие | Что ждём |
|---|---|---|
| Статика собирается | `pnpm generate` | Сборка без ошибок, страницы предрендерятся |
| Дев-сервер поднимается | `pnpm dev` | Стартует на `:3000`, в консоли нет ошибок |
| Лендинг открывается | `/` | Тёмный лендинг, анимация hero, кнопки |
| In-portal страницы рендерятся вне фрейма | `/app`, `/import`, `/settings`, `/login`, `/queues` | Отдаются без белого экрана (SDK молча no-op вне портала) |
| Backend жив | `GET /api/health` | `{ status, time, commit }` |

## Уровень 2 — просто прогнать (happy-path)

Цель — прогнать основной сценарий один раз. Критерий: один документ проходит весь путь до записи
в CRM, уведомление в чат приходит.

| Область | Действие | Что ждём |
|---|---|---|
| Авто-проверки | `pnpm check` (lint + typecheck + test) | Всё зелёное (сейчас 333 теста) |
| Ручная загрузка | на `/app` перетащить/сфотографировать прайс/накладную (зона загрузки вверху) | Файл принят, статус в «Последних операциях» |
| Очереди | `docker-compose up`, `/queues?preview=1` | График очередей рисуется |
| Пайплайн | документ → `file-extract → agent-run → crm-sync` | Джоба доходит до конца, статус `done` |
| Живой REST (вебхук) | точечно: диск (папка+файл), `im.message.add`, `crm.product.list` | Отрабатывают (проверено вживую) |
| Установка в портал | `/install` на тестовом портале | `event.bind` + `installFinish`, токен на backend |

## Уровень 3 — со всех сторон (полное покрытие)

Цель — граничные случаи, безопасность, отказоустойчивость, регрессия. Критерий: все граничные
случаи ведут себя предсказуемо (ошибка → в чат ошибок, без потери строк), безопасность закрыта,
после падений система восстанавливается.

### Функционально / данные

- Форматы входа: PDF-текст, скан (OCR рус/бел/каз), office, `1CClientBankExchange`, client-bank `^Type=`.
- НДС: с НДС / без НДС / разные ставки по строкам / «включён ли НДС» не определён → жёсткая ошибка
  (не создаём кривую сущность, не теряем строки).
- Товар: по артикулу (попал / не попал + фолбэк на имя), `onMissing` = skip-warn / freeform
  (создание товара удалено — слишком сложная операция для мультитенант-импорта).
- Поставщик: найден / не найден (создаём без компании + предупреждение).
- Валюта не в портале → ошибка в чат, сущность не создаём.
- Идемпотентность: повтор джобы → не дублирует сущность и не шлёт второй раз «успех».

### Безопасность

- BB/промпт-инъекция в назначении/имени → нейтрализация перед чатом (`[url]`, упоминания, кнопки).
- Мультитенант-изоляция: чужой `member_id` / чужой `app.option` недостижимы.
- Агент (DeepSeek) не видит токенов Б24; sanitized env; запрещённые тулы.
- Загрузка: превышение размера → 413; нет Redis → 503; traversal в пути файла.
- Операторская авторизация: неверный пароль, брутфорс-троттлинг (`limit_req`), подпись cookie.

### Отказоустойчивость / инфраструктура

- Redis/Postgres упал и поднялся; ретраи джоб; синхронный фолбэк приёма событий Б24.
- Удаление приложения → чистка данных портала (токены, дедуп, файлы).
- TTL-выметание старых загрузок.
- Docker: сборка `backend`-образа с бинарями извлечения; `healthcheck`; `docker-compose.prod`.

### Нагрузочное тестирование очереди — ✅ ЧАСТИЧНО (2026-07-28): механика очереди подтверждена

**Цель:** при массовой загрузке приложение **не отказывает и не теряет документы**, а *держит
очередь и постепенно всё обрабатывает*. Провал — это отказ в приёме, потерянный документ или
задвоенная сущность; медленно, но всё дошло — это успех.

> ⚠ **Что именно прогнано.** Проверена **механика очереди** (BullMQ + Redis) и **темп обработки в
> ритме лимитера Битрикс24**. Реальных REST-вызовов к порталу в прогоне нет — обработчик
> смоделирован. Поэтому нагрузочное тестирование **не закрыто целиком**: пункты про живой портал,
> падение инфраструктуры, TTL и UI остаются (список ниже).

**Команда:** `pnpm loadtest:queue` (скрипт `scripts/load-test-queue.mjs`, dev-only). Гоняет
**настоящие** BullMQ `Queue`/`Worker` на локальном Redis с **теми же** настройками лока, что в бою
(`crmLockTuning`; совпадение стережёт `tests/loadTestQueueParity.test.ts`), но с обработчиком-моделью.
Каждый сценарий работает в своей временной очереди и подчищает её за собой — в том числе при падении.

```bash
pnpm loadtest:queue                                              # 120 документов, 6 порталов, 3 воркера
pnpm loadtest:queue --jobs 2000 --portals 20 --workers 4 --concurrency 4
pnpm loadtest:queue --skip-slow                                  # без сценария реального темпа (~12 с)
```

**Гард безопасности.** Скрипт **отказывается** работать, если `REDIS_URL` указывает не на локальный
Redis (обходится явным `--allow-remote-redis`): он создаёт тысячи задач и удаляет свои очереди, а
`REDIS_URL` часто наследуется из окружения с боевыми значениями. Пароль из URL в лог не печатается.

> **Поднимайте Redis с `--dir`:** `redis-server --daemonize yes --dir /tmp`. Запущенный из корня
> репозитория Redis кладёт свой `dump.rdb` прямо туда — один раз этот файл так и уехал в коммит.
> Артефакты закрыты в `.gitignore`, а `tests/noLocalArtifacts.test.ts` не даёт им попасть в индекс
> снова, но проще не создавать их вовсе.

#### Покрыто этим прогоном

| Сценарий | Итог |
|---|---|
| Массовая загрузка (до 2000 документов от 20 порталов) | все обработаны, каждый **ровно один раз**; сверено не только счётчиком обработчика, но и состоянием в Redis (`completed`/`failed`) |
| Разгрузка backlog | очередь монотонно уходит в ноль, без залипания |
| Ограничение параллелизма | пик = ровно `воркеры × concurrency`, сверено и по обработчику, и по `getActiveCount()` из Redis |
| Повторная отправка документа | три постановки → одна задача, обработчик вызван один раз |
| Обрыв воркера в середине пачки | задачи зависли в «в работе» → **передоставлены** новой реплике → все документы дошли, очередь пуста |
| Несколько реплик | ни одна задача не досталась двум репликам, нагрузка распределена |
| Приём под нагрузкой | постановка поверх backlog из 200 задач: p95 = 1 мс |
| **Реальный темп (лимитер Б24)** | обработка в ритме ~2 зап/с на портал: время разгрузки упирается в лимитер, а не в очередь |

**Единственная цифра, имеющая отношение к бою:** при ~8 REST-вызовах на документ и лимите ~2 зап/с
на портал получается **≈ 900 документов в час на портал**. 1000 документов одного портала очередь
разгребёт примерно за час — она их **держит**, но быстрее лимитер не даст.

> Пропускная способность «сотни док/с», которую печатают сценарии 1–5, — это скорость **Redis и
> BullMQ на модели**, а не приложения. Как метрику приложения её использовать нельзя.

Остальные цифры прогона (время разгрузки, профиль очереди, число передоставленных задач)
**ориентировочны**: зависят от машины и тайминга, от прогона к прогону отличаются. Это не пороги
регрессии, а иллюстрация поведения.

**Оговорка по сценарию обрыва.** В бою лок держится 60 с (`crmLockTuning`) — ждать столько в тесте
бессмысленно, поэтому этот сценарий гоняет **тот же механизм с ускоренным локом 2 с**. Проверяется
**путь восстановления**, а не сама величина таймаута.

**Главный вывод.** Очередь даёт гарантию **«хотя бы один раз»**, а не «ровно один раз»: задача,
которую воркер держал в момент падения, зависает и возвращается по stalled-проверке, после чего
обработчик берёт её **повторно** (прогон это подтверждает assert-ом, а не наблюдением). От задвоения
сущности в CRM защищает **не очередь, а маркер идемпотентности** (`originId`/`xmlId` + поиск перед
созданием). ⚠ Оговорка: это закрывает **последовательную** переобработку (упавший воркер). Гонка
из #163 — **живой, но потерявший лок** воркер параллельно со второй репликой — этим прогоном не
воспроизводится и остаётся открытой.

#### НЕ покрыто (осознанно, нужен живой портал или инфраструктура)

- **Реальные REST-вызовы к Б24** и поведение `RestrictionManager` под нагрузкой
  (`QUERY_LIMIT_EXCEEDED`) — отдельный `pnpm loadtest:123` и E2E `pnpm live:crm --ai`.
- **Ретраи упавших джоб** (`attempts`/`backoff`), поведение при ошибке обработчика, набор `failed`
  после исчерпания попыток — обработчик в прогоне всегда успешен.
- **Обрезка Redis** (`removeOnComplete`/`removeOnFail`) при непрерывном потоке.
- **Падение и возврат Redis/Postgres** под нагрузкой.
- **TTL заданий** (`IMPORT_JOB_TTL_HOURS`) при очень длинной очереди.
- **UI под нагрузкой** (`/queues`, «Последние операции», счётчики) — проверяется вручную.
- **Пиковая память/CPU воркера** — не замеряются.

### Доступность

- **Скринридер на «Последних операциях»**: убедиться, что стёпер (`role="status"`, «Стадия: …»)
  даёт не меньше полезного, чем убранная полоса прогресса — пользователь слышит название текущего
  этапа при смене статуса.
- Все иконочные кнопки имеют текстовую подпись; фокус виден; управление с клавиатуры работает.

### Регрессия / визуал

- `pnpm check` в CI; сборка Docker-образа на каждом PR.
- Визуальная проверка страниц (свет/тёмная, мобайл/десктоп).
- Прогон реальных фикстур выписок/прайсов.
