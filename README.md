# AI-импорт прайсов — приложение Маркета Bitrix24

> Last reviewed: 2026-08-11

Облачное приложение Битрикс24 Маркета (мультитенант, OAuth). Сотрудник загружает документ с
таблицей — накладную, счёт, коммерческое предложение или прайс, — приложение распознаёт его
нейросетью, находит поставщика и вносит позиции в нужную сущность CRM.

Издатель — ИП Шевчик И.С.

## Стек

Nuxt 4 + Nitro **одним процессом**, BullMQ + Redis (очереди), Postgres (токены порталов и счётчики),
интерфейс на Bitrix24 UI. Распознавание — OpenAI-совместимый вызов: BitrixGPT по умолчанию, DeepSeek
или свой эндпоинт как опция.

Все обращения к Битрикс24 идут через официальный SDK со встроенным ограничителем запросов.
Модель работает **без инструментов**: получает текст, возвращает JSON — и всё.

### Подсистемы: правила, обязательные к соблюдению

⚠ **Это не обзор, а инварианты.** Они переехали сюда из `CLAUDE.md` 11.08.2026: тот грузится в
контекст каждой сессии целиком и упёрся в свой потолок (#508), а эти правила нужны только тому,
кто правит соответствующую подсистему. **Правишь `server/` или `app/` — прочитай нужный пункт
здесь; нарушение стоит ровно столько, сколько написано рядом.** Разбор «почему так и что
ломалось» — [`docs/PROCESS.md`](docs/PROCESS.md) §14, состояние подсистем —
[`docs/PROJECT_MAP.md`](docs/PROJECT_MAP.md).

- `app/` — Nuxt (авто-импорт): `utils` (чистое ядро + тесты) / `composables` / `config` / `types` /
  `components` / `pages` / `layouts`.
- `server/` — Nitro backend: `api` / `routes` (не-`/api` публичные роуты) / `utils` (чистые с DI) /
  `queue` (BullMQ) / `db` / `plugins` / `agent`.
  - **SEO лендинга** (#292): share/SEO-мета живёт в `app/pages/index.vue`, **не** в корневом `app.vue`.
    Разбор — [`PROCESS.md`](docs/PROCESS.md) §14.11. Правила: `og:image` и `canonical` **обязаны быть
    абсолютными**; **canonical/OG лендинга всегда указывают на прод и env игнорируют** (#304) —
    канонический дом ровно один. База **разбирается `new URL`, а не проверяется регуляркой** (префиксная
    проверка пропускала перевод строки, `@` и query). Гард — `RUN` в `Dockerfile` после `pnpm build`.
    ⚠ **`public/og.png` собирает РУЧНОЙ `pnpm og`** (#329), разметка — `scripts/lib/ogTemplate.mjs`,
    штамп `public/og.stamp.json` несёт два хэша (разметки и байт PNG) — правка текстов или вёрстки без
    пересборки роняет CI. **Не по mtime** — git времена не хранит. ⚠ **`LANDING_DESCRIPTION` — своя
    строка, НЕ псевдоним подзаголовка**: валидаторы карточек ждут 90–155 знаков, длина закреплена тестом.
    Бейдж — `app/config/brandBadge.ts`, цвета **в oklch, как в палитре Tailwind v4**.
    ⚠ `/robots.txt` + `/sitemap.xml` — **роуты**, не статика, и **без суффикса `.get`** (h3 не подменяет
    HEAD на GET) ⇒ `crawlerRoute.crawlerMethodGate` возвращает 405 с обязательным `Allow` и 204 на OPTIONS.
    Композиция «сырой env → проверенная база → тело» живёт в одной `seoFiles.crawlerFiles`.
    ⚠ `siteUrl`/`buildDate` читаются в рантайме ⇒ обе переменные обязаны стоять и на рантайм-стадии образа.
    ⚠ Служебные страницы несут `robots:noindex`, но в `robots.txt` **НЕ закрыты**: `Disallow` и `noindex`
    — альтернативы, а не слои. В `DISALLOWED_PATHS` только `/api/`. Инвариант «индексируется только
    лендинг» заявлен **над страницами**, а не над конфигом — тест рекурсивно обходит `app/pages`.
    ⚠ **Граница гарда**: статика вне `app/pages` (`public/b24-form.html`) им НЕ видна — у неё свой
    `noindex` в самом файле. Кладя новую статическую HTML-страницу в `public/`, не рассчитывай на
    гард: он до неё не доходит, а «рекурсивно обходит страницы» читается как «покрыто» и создаёт
    ложную уверенность.
    ⚠ **Работа на сервере клиента обещается «по запросу»** (#96), и оговорка «текст документа всё равно
    уходит к поставщику модели, свой сервер не делает контур замкнутым» стоит **на лендинге** размером и
    яркостью как основной текст: раньше её видели только уже установившие приложение.
  - **LLM-экстрактор — OpenAI-совместимый chat-вызов** (`server/agent/`, tool-less, чистый text→JSON:
    инъекция документа не может ничего кроме JSON). `llmConfig.ts` (резолвер `LLM_PROVIDER`) →
    `chatExtract.ts` (`runChatExtract`, `response_format:json_object`, ретрай через общий `retry.ts`,
    `validateExtractedDocument` + гард `MAX_ITEMS`) → `openaiChat.ts` (адаптер на `openai` SDK,
    `maxRetries:0`). **BitrixGPT** — дефолт (инференс в экосистеме Битрикс; этим снят юр-блокер #215),
    **DeepSeek** — опция (юрисдикция КНР). Ключи: `DEEPSEEK_API_KEY`, `BITRIXGPT_API_KEY`/`VIBE_API_KEY`.
    Разбор — [`PROCESS.md`](docs/PROCESS.md) §14.11 и §6.9/§6.10.
    ⚠ **Что о провайдере писать НЕЛЬЗЯ** (#437, закреплено тестом): фразы «данные не используются для
    обучения» не должно быть **ни в каком виде** — правообладатель вправе обучать на переданных запросах.
    ⚠ Версию модели публично не называем. ⚠ **Автоматического переключения провайдера НЕТ** — тексты
    обязаны говорить «если Издатель переключит обработку», а не «при недоступности основного канала».
    ⚠ **Отказ провайдера → внятный текст, а не строка провайдера** (`llmFailure.ts`, #416): наружу уходит
    ТОЛЬКО наш текст. Ключ проверяется ПЕРЕД квотой, недоступность — перед «не разобрался», неузнанное →
    `unknown`. Ни один текст не обещает автоматического повтора — его нет. В журнал идёт класс + подпись
    **по белому списку** (`llmErrorSignature`), коды заданы ЗАКРЫТЫМИ списками, а не формой.
    ⚠ Гарантия НЕ покрывает голое трёхзначное число 400–599. **Наши собственные отказы** помечаются
    полем `own` и доезжают СВОИМ текстом. ⚠ **`LLM_PROVIDER` роняет сервис на старте** на неизвестном
    значении и на `custom` без `SELF_HOSTED=1`; отсутствие ключа фатальным НЕ считается.
    ⚠ Живая находка: AI Router принимает `Bearer` только для ключей `vibe_*`.
  - **crm-sync — запись документа в сделку** (`queue/crmSyncCore.runCrmSync`, чистое ядро с DI,
    тесты; транспорты `crmWrite`/`companyLookup`/`productLookup`/`offerLookup`/`measureList`,
    проводка `liveDeps`). ⚠ **Свод инвариантов — [`PROCESS.md`](docs/PROCESS.md) §15.1**: цена и
    НДС, подбор товара, единицы, идемпотентность, код владельца строк, цель и роутинг, дело в
    таймлайне, журнал. Правя эту подсистему, прочитай его целиком — половина правил выглядит как
    усложнение, и разбор каждого лежит в §14.
  - **Адрес возврата в приложение — `/marketplace/app/<ID>/`, НЕ `/marketplace/view/<код>/`**
    (`portalAppUrl` + `appInfo.fetchAppId`, #385, живой прогон владельца 09.08.2026): символьный код
    принадлежит карточке МАРКЕТА, а установленное приложение адресуется **локальным идентификатором
    установки** — пока приложение не опубликовано, символьного адреса не существует вовсе, и первая
    редакция ссылки на портале просто не открывалась. `ID` отдаёт `app.info`, метод отвечает
    **только в контексте приложения** (вебхуком не позвать ⇒ живые скрипты ссылку не получают —
    ожидаемо). ⚠ Фолбэка на символьную форму НЕТ: адрес, работающий на одном классе порталов и
    дающий 404 на другом, — это ровно та мёртвая ссылка, которую правило запрещает. ⚠ Домен ИЛИ
    идентификатор неизвестны ⇒ строки со ссылкой нет вовсе. ⚠ Идентификатор мемоизируется на джобу
    вместе с доменом: на одном отказе адрес нужен и личному сообщению, и чату ошибок, а без мемо это
    лишний SELECT и лишний REST на каждого получателя.
  - **Сообщения в чат — от имени приложения** (`chatBot.ts` + `chatNotify.sendChatMessage`, #316):
    `im.message.add` пишет **от владельца токена**, поэтому отчёты читались как отчёты сотрудника.
    Актуальная пара — **`imbot.v2.Bot.register` + `imbot.v2.Chat.Message.send`** (скоуп `imbot`), старые
    `imbot.register`/`imbot.message.add` DEPRECATED. Регистрация — **на установке**. Разбор —
    [`PROCESS.md`](docs/PROCESS.md) §14.11.
    ⚠ **Старый путь — обязательный фолбэк, не запас**: на бесплатном тарифе боты недоступны, есть предел
    числа ботов, а порталы до появления скоупа его не выдавали. ⚠ Фолбэк только на **брошенное
    исключение**: ответ непонятной формы означает, что сообщение скорее всего доставлено. Отказ
    запоминается на 6 ч. ⚠ В лог идёт только **код** ошибки: текст REST-ответа может процитировать
    параметры вызова, а они несут текст документа. ⚠ **Удаление** — при деинсталляции **до** удаления
    строки портала. ⚠ **Профиль** — отдельный `Bot.update`: регистрация идемпотентна и данные НЕ
    перезаписывает. ⚠ **На отказ регистрации идёт поиск уже заведённого бота** (`Bot.list` по нашему
    коду): на переустановке `Bot.register` существующего не отдаёт (`BOT_CODE_ALREADY_TAKEN`).
    ⚠ **Аватар только в `Bot.update`** и на любой отказ — один повтор **без аватара**: иначе отвергнутая
    картинка не применяла бы НИЧЕГО и бот остался бы безымянным навсегда. ⚠ **Бот пишет только в чат,
    где он СОСТОИТ**: на отказ отправки идёт `im.chat.user.add` и один повтор — реактивно, а не проверкой
    участия перед каждым сообщением. Личный диалог не трогаем. ✅ live-verified 2026-08-02, цепочка
    замкнута целиком.
  - **Событие install/uninstall — через очередь** `b24-events` (порт из client-bank): роут
    `api/b24/events.post.ts` верифицирует и **кладёт в очередь**, консьюмер (`queue/handlers.handleEventJob`)
    — **единственный писатель** `portal_tokens`; при недоступности Redis роут пишет **синхронным
    фолбэком** (B24 online-события не ретраит). Порядок событий защищает **тумбстоун** `portal_tombstone`
    (#77): stale/out-of-order install не воскрешает удалённый портал (гард в `tokenStore.saveToken/deletePortal`
    по `eventTs` = top-level `ts` вебхука). **Рост тумбстоунов ограничен TTL** (#77): ежечасный `retentionSweep`
    сносит `portal_tombstone` старше `tombstoneDays` (env `TOMBSTONE_TTL_DAYS`, дефолт 30 д, кламп [1,365]) — гард нужен лишь чтобы пережить
    late/retried install той же деинсталляции (часы), а не месяцы; иначе копилась бы строка на каждый
    навсегда-удалённый портал. `deleted_ts` — `ts` в **секундах**, сверка с `EXTRACT(EPOCH FROM now())`
    unit-safe by construction (мс-значение просто никогда не подметётся, а не удалится рано). **Привязка member_id к OAuth-гранту на первой установке**
    (`verifyInstallMember`, #162): `verifyInstallToken` доказывает контроль **домена** (вызов `profile`), но не
    member_id — поэтому дополнительно рефрешим присланный `refresh_token` и сверяем **authoritative** member_id из
    ответа токен-эндпоинта с присланным `ev.memberId` (mismatch → 403; forged grant `invalid_grant` → 403;
    network/`wrong_client` → 503, fail-closed). Так поддельная установка (валидный токен своего портала + чужой
    member_id) не отравит member_id жертвы. Рефреш **ротирует** токен ⇒ на успехе храним **возвращённый** грант,
    а не присланные креды. Гейт на `B24_CLIENT_ID/SECRET` (без них рефреш невозможен в принципе). Тумбстоун
    неатомарен, но TOCTOU-free — событийный воркер
    **single-instance**.
  - **Роль-сплит воркеров** (`queue/runtime.ts`, scale-out): роли `QUEUE_WORKERS`/`QUEUE_CRON`.
    `startEventWorker` (события) идёт **только на primary/cron-инстансе**; `startThroughputWorkers`
    (extract/agent/crm-sync) масштабируется на N реплик (`worker`-контейнер, `QUEUE_CRON=0`). Гейтинг — в
    `plugins/queue.ts`. Per-queue concurrency — отдельно (`QUEUE_EXTRACT/AGENT/CRM_CONCURRENCY`,
    `worker.queueConcurrency`, #95).
  - **Рефреш OAuth-токена сериализован per-portal** (`utils/dbLock.withAdvisoryLock`, `ensureAccessToken`,
    #35): advisory-lock + re-read внутри лока → портал рефрешится ровно раз, без гонки на ротации
    refresh-token. Персист — `updateTokensOnRefresh` (UPDATE-only, не воскрешает удалённый портал); строка
    исчезла под локом ⇒ рефреш не делаем. Сам refresh идёт **через SDK** (`b24Sdk.sdkRefreshTransport` →
    `B24OAuth.auth.refreshAuth`), ограничен таймаутом (гонка — у SDK-axios рефреша нет своего таймаута), чтобы
    зависший OAuth не запинил лок + соединение пула. **Область**: этот путь — у **keep-alive крона**
    (`ensureFreshToken`, single-instance) и кнопки reauth (`portalReauth`). **crm-sync hot-path им НЕ ходит** — там транспорт
    `@bitrix24/b24jssdk` рефрешит **реактивно** (свой per-job `B24OAuth`, `setCallbackRefreshAuth`→персист),
    без advisory-лока: при scale-out throughput-воркеры могут ротануть один портал параллельно, но персист
    UPDATE-only идемпотентен, а SDK-лимитер гасит всплеск — гонка безопасна, лишь возможен лишний рефреш.
  - **REST-транспорт к порталу (crm-sync) — `@bitrix24/b24jssdk`, единственный** (`utils/b24Sdk.ts`,
    адаптер `B24OAuth`→`SdkTransport` `{ call, list }`): `call` — одиночный `RestCall`, `list` —
    **полная выборка списка** (`SdkListCall`, SDK сам пагинирует keyset-ом по `ID` через
    `actions.v2.callList.make` — ручной пейджер на этом транспорте не нужен). У SDK встроенный
    **RestrictionManager** (пер-портальный leaky-bucket лимитер + адаптивный operating-backoff). **In-SDK
    ретрай ОТКЛЮЧён** (`disableSdkRetry`, #123: `maxRetries:1`, `retryOnNetworkError:false`) — crm-sync
    создаёт НЕидемпотентные сущности (`crm.item.add`/`crm.product.add`), ретрай такого вызова после
    client-timeout/504 задвоил бы (Битрикс не гарантит уникальность `originId`/`xmlId`); целый джоб ретраит
    **BullMQ** (там create идемпотентен — find-before-create по маркеру). Find-before-create — TOCTOU: защищает
    **последовательные** ретраи (crash-recovery), но не **конкурентную** stalled-переобработку одного джоба
    (#163). Полный advisory-lock отклонён — держал бы pooled pg-соединение на REST-create при `pool max 5` →
    голодание пула на scale-out; вместо этого **тюнинг BullMQ-лока crm-воркера** (`crmLockTuning`:
    `lockDuration` 60с > дефолт 30с — живой воркер продлевает лок и не «протухает» ложно → второй воркер не
    стартует конкурентно; `maxStalledCount:1` — один recovery-редоставки для реально упавшего джоба). Остаются: проактивный rate-throttle,
    адаптивный backoff, реактивный OAuth-рефреш (`setCallbackRefreshAuth` → персист `updateTokensOnRefresh`,
    UPDATE-only). **Live-верифицирован** на `bel.bitrix24.by` (`pnpm sdk:smoke`: profile+crm.item.list+burst 30
    без `QUERY_LIMIT_EXCEEDED`). `makePortalSdkCall` строит `B24OAuth`; резолвер `createPortalSdkResolver` (#123/#163,
    порт из client-bank) **мемоизирует один клиент на портал** (единый лимитер-бакет + одна загрузка токена
    на джобу — раньше `need()` строил ~9 клиентов на джобу). Кэш безопасен при внешней ротации
    refresh-токена (сосед/keep-alive-крон) двумя клапанами: короткий **TTL** (`SDK_CLIENT_TTL_MS` 60с) +
    **evict-on-error** (упавший вызов дропает клиент → следующий resolve пересобирает из свежего DB-токена
    сразу, без вечного `invalid_grant`). На процесс с forever-кэшем НЕ полагаемся — самозаживает. Ручной
    `makePortalRestCall` удалён. Общий билдер
    `sdkPortalDeps(SdkInfra)` связывает `SdkPortalDeps` со стором/env — им пользуются и `liveDeps.restResolver`
    (crm-sync), и frame-token роут `catalog-properties` (читает по OAuth-токену портала: `resolveFrameMember`
    верифицирует фрейм-токен → `member_id`, дальше SDK). Чистые мапперы +

## Быстрый старт

```bash
cp .env.example .env          # заполнять для локальной работы почти ничего не нужно
docker compose up -d db redis # Postgres и Redis из compose-файла репозитория
pnpm install
pnpm dev
```

Приложение поднимется на `http://localhost:3000`. Без Redis очереди не работают: страница откроется,
но загрузка документа получит отказ «сервис обработки временно недоступен» — это ожидаемо, а не
поломка. Все переменные с пояснениями — в `.env.example`.

**Живые проверки против настоящего портала** (`pnpm verify:*`, `pnpm live:crm`) требуют вебхука
тестового портала в `.env.b24test` и ключа нейросети. Оба файла в репозиторий не коммитятся —
координаты берутся у владельца.

## Разработка

- **В `main` не пушим** — только через PR. Мержит владелец.
- Комментарии — по назначению: короткая подпись «что это» по-английски, разбор «почему именно так»
  по-русски. Всё, что видит пользователь, и документация — по-русски.
- Чистые функции отделены от ввода-вывода и покрыты тестами; данные из портала выводятся только
  через экранирование.
- Каждый документ в `docs/` и в корне несёт строку `> Last reviewed: ГГГГ-ММ-ДД`.

Подробнее — [`CLAUDE.md`](CLAUDE.md).

## Производительность

**≈ 900 документов в час на один портал.** Упирается в ограничитель Битрикс24 (около 2 запросов в
секунду), а не в очередь: очередь backlog держит и разгребает полностью, приём нового документа
остаётся мгновенным. Подробности — [`docs/PROCESS.md`](docs/PROCESS.md) §13.
